# Brief A1: notation and types

Folder: `scratch/rewrite/a1/`. Read `briefs/COMMON.md` first.

## Question

Does the notation of the spec parse without ambiguity? Is the type system complete enough to check
a model?

## Read

- `scratch/rewrite/spec.md`, all of it. For notation: "How to declare, read and change a value",
  "Primitive and composite types", "Units, comparisons and layout", "Collections, keys and
  projections", "Formulas and the values a caller can read", "Model text, status cases and
  evidence", "Distributions and explicit draws", every code block of the flow, solver and event
  parts, "Expressions and instantaneous transfers", "Open design questions".
- The present front end, at the base commit: `napkin/model/language/lex.py` (lines, indentation,
  tokens, units, texts), `napkin/model/language/expressions.py` (today an expression is written as
  Python text and parsed with `ast`; that route cannot read `<a, b>`, `<->` or a trailing
  `in [lo, hi]`), `napkin/core/expr.py` (the typed nodes), `docs/language.md` section 2.1 (the
  present notation of units and numbers).

## Method

1. **Corpus.** Put every fenced `text` block of the spec in `corpus/NN-name.scn`, and each `csv`
   block in `corpus/data/`. Put the notation that the spec shows only inline in `corpus/inline.txt`,
   one per line, with its kind (declaration, statement, expression). Examples of inline notation:
   `priority(customers.by(rank).delivery)`, `Reading.instances.by(hour).at(t).factor`,
   `move amount from this.supply to batch`, `ok = (samples.draw() in [lo, hi])`,
   `input repair_time = uniform(1 h, 3 h).draw() in [1 h, 12 h]`,
   `net_change: L = 0 in [-20, 20]`, `weekly_unserved: people = none @no_cohorts`,
   `count(this.service_restored.occurrences) > 0 and since(this.service_restored) >= 3 h`,
   `minimize(sum(places.where(critical).unmet))`.
2. **Parser.** Write `parser.py`:
   - a tokenizer. Start from the rules of `lex.py` and say what had to change;
   - a precedence parser for expressions. Give `napkin.core.expr` nodes where a node kind exists,
     and small node classes of your own where none does: a collection literal, a path with calls
     (`.where(...)`, `.by(...)`, `.at(...)`, `.draw()`, `.start(...)`), `formula(...)`, a
     membership test, a quantity with its unit;
   - a parser of lines and blocks: `name: type = expr`, `readonly`, `input`, a trailing
     `in [lo, hi]` (also on a continuation line), `@record`, texts, `flow name: a -> b`, `<->`,
     nested legs, property initializers, `event(...)`, `after D:` with an optional `when C`,
     `until C`, a trigger `when C:` with `reset when` or `reset after`, `switch`, `move`, `+=`,
     `solver:` with its four sections, `status <rating>` with an optional `when C`, `assert`,
     `record`, a table `name: Template from "file.csv"`.
   It need not resolve names or check units. It must give a tree, and it must refuse what is
   ambiguous.
3. **Run it** on the whole corpus. Write `parse_report.md`: each file, parsed or the error.
4. **Hunt ambiguities.** For each item below give the grammar rule, two inputs that tell the
   alternatives apart, and what the parser does:
   - `<` and `>` as comparisons, as the brackets of a collection literal (`<this.primary,
     this.backup>`, `<>`), and in a type (`<Pump>`);
   - a trailing `in [lo, hi]` as a range, against a membership test as an initializer;
   - `->` and `<->` against a comparison with a unary minus (`a < -b`, `a<-b`);
   - unit arithmetic: `48 h / 2` against `48 h/2`; `L/h^2`; `0.5 Wh/L`; `(2 h)`; `^` against `**`;
     the present rule that `-` multiplies units; a number before a name that can be a unit or a
     value. Propose one rule. List what it changes in the present notation;
   - `=` as a declaration or an assignment, against `==`;
   - bare enum members (`OPEN`), with and without an expected type;
   - `status` as a field name inside an event, against the `status ok when ...` display line;
   - `when` after `after D`, against a trigger's `when C:`; `reset when false`;
   - `formula(bool)` where a type stands, against `formula(expr)` where a value stands;
   - `#` comments, `#` inside a text, escaped quotes, wrapped clauses;
   - the reserved words. Propose the list (`from`, `to`, `in`, `this`, `none`, `SOURCE`, `SINK`,
     `t`, ...), and say which present model names it would break. Check with a search of
     `examples/` and `scenarios/` at the base commit.
5. **Types.** Write `types.md`: a first type system that can check a model. The types: bool, enum,
   number with a dimension and an optional range, text, `formula(T)`, distribution, the kinds of
   flow, a store, a collection `<T>`, a template and a reference to an entity, event, trigger,
   occurrence, solver. For each: what can be read, what can be written, and by whom (the spec's
   table "What each scope can see" is the start). Rules for inferring the type of an initializer,
   and where the declaration gives a literal its unit.

## Rulings that you owe

Unit arithmetic. `<...>` beside comparisons. Wraps, escapes and comments. Reserved words and
shadowing. Enum names with no expected type. The type of a property that takes "a rate or a live
formula" (`.request`). Assignment and copy of a formula. Reference parameters: a stock, against a
copy of its value. The names of triggers, and whether an event can have several. Whether `.start`
gives a handle. Distribution constructors, and the range of a draw (bounded, unbounded,
transformed). Whether a `run` path exists in source.

## Exit

`corpus/`, `parser.py` (`python parser.py corpus/` prints a summary line for each file),
`parse_report.md`, `types.md`, `FINDINGS.md`. The whole corpus parses, or each failure has a ruling
that says how the spec's notation must change.
