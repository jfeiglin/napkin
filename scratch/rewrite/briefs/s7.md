# Briefs S7-F and S7-E: breakpoints, checkpoints and edits

Read `briefs/COMMON-B.md` first, then `PLAN.md`, "Changes after G0", items 10 to 15. Item 15 is
this slice: the owner's decision, the rule of exact resume, the rules of edits and the acceptance
example. State files: `scratch/rewrite/b1/s7-front/STATE.md` and `b1/s7-engine/STATE.md` (60 lines
at most). The rules of COMMON-B hold.

The slice comes in milestones, and the owner asked for the first ones first: the loadable compiled
program (S7-F, M1) and the checkpoint with exact resume in a fresh process (S7-E, M1). The estimate of
"one slice" is provisional until the numerical resume case of S7-E's M1 passes. Report at M1 if
usage runs short; the later milestones can go to fresh agents.

## S7-F: the artifact, the contract and the front end

Own `napkin/model/`, `napkin/program/` (but `napkin/program/checkpoint.py` and the trace kinds of
`record.py`, which are S7-E's), `tests/language/`, `tests/model/`, `tests/program/` (with
`examples.py`) and `tests/reference/`.

- **M1, the loadable program.** A versioned artifact: the program's canonical bytes
  (`canonical.py`) and a loader that gives back an equal program, with a version header that refuses
  another format or language version by name; and a side table, made by the compiler, that maps each
  executable location (event, stage, statement, trigger) to its kind and source place (file, line,
  column), and each value to its name, label (first text) and evidence. The side table is outside
  the program's identity, so a label edit moves no key. Tests: compile, save, load in a fresh
  process (a subprocess), the same program bytes and the same record of a run.
- **M2, no player machinery.** `choose(...)`, `sees`, actor controllers and picks leave the
  language, the program (`config.py`'s controllers and picks) and the oracle, each refused by name
  with a hint (store the value in a field and branch on it; a wrapper can pause before the branch).
  The four `dispatcher_*` examples become the acceptance example of `PLAN.md` item 15: the forecast
  drawn into an occurrence field `order`, a `switch` on it, eligibility as a case guard. The oracle
  gets breakpoints and edits, written from item 15 and not from the engine: resume reruns the
  paused stage from its start, then applies the edits in order.

## S7-E: the engine

Own `napkin/engine/` (the solve library included), `tests/engine/`, `napkin/program/checkpoint.py`
and the trace kinds of `napkin/program/record.py`.

- **M1, checkpoint and exact resume.** A breakpoint at a location of the compiled program (event,
  occurrence, stage, statement; the S4b pause of a choice is the first case of it) stops the run
  and gives a checkpoint: the logical state of the run (values, occurrences and where each waits,
  the pending work of the moment and later, trigger states, draw counters, the record so far) and
  where and why it stopped. It is a documented representation, not a pickle of engine objects. A
  fresh process loads it with the program and resumes. The rule: the same recorded values, draw
  results, event times and event order as the run straight through. Find what carries numerical
  state across a moment today (integrators of sets that a moment does not touch, the kept HiGHS
  instance's basis, caches) and make the future of a run depend only on its logical state, on every
  path: either save that state as data, or restart it at each moment on every path, the
  uninterrupted one included. Restarting only on the resume path is wrong (it makes the two resumed
  runs agree with each other and differ from the uninterrupted one). Measure what the choice costs.
  A breakpoint inside a stage resumes by rerunning the stage from its start. Tests, each three ways
  (no breakpoint; pause and resume in one process; save and resume in a fresh process): a
  continuously changing value near a trigger threshold; a pause inside a stage that has drawn,
  queued a child and written; a declared solver between two solves; each way of running.
- **M2, edits.** An edit of a live stored value at a checkpoint: types and bounds hold; derived
  values and rates are recomputed by the usual rules; a finished occurrence is frozen (refused); an
  edit inside a stage joins that stage's writes (the stage sees it, others when it commits), an
  edit between rounds commits at once. An edit of a store is an external transfer in its books;
  an edit that lowers a value whose never-falls proof the report would use withdraws that proof for
  the run (the report says why). Each edit is a trace entry (time, breakpoint, target, old, new).
  Rerunning a stage's prefix keeps the edits made so far, in order: two pauses in one stage neither
  lose the first edit nor apply it twice. The acceptance example of item 15, against the oracle.
- **M3, no player machinery in the engine.** Remove controllers, picks, the choice instruction, and
  `Run.resume(*picks)`; `napkin.engine.paused` becomes the checkpoint interface.
