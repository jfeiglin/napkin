# The owners of the engine's decisions

## Why this map exists

A decision of the engine is a rule that gives one answer: for example, "is this stock on its bound?"
or "which branch of a formula applies after a switch?". When two places in the code calculate the
same decision, they can give different answers at a tie, on another platform, or after a change to
one copy. An audit found that fixes of single cases left their causes in other copies
([change 21](../design/decisions.md#change-21)). So each decision has one owner: one file and one
function. Every other place that needs the answer reads the owner, and supplies its own operands, state
or time. Then a rule has one copy.

This page is the map. For each decision it gives:

- **Owner**: the file and the function that decide.
- **Readers**: the code that calls the owner or supplies its operands.
- **Tests**: the tests that check the decision. A name such as `stage_scalar` is a family of the
  generated corpus ([verification.md](verification.md#the-generated-corpus)).

A path that does not start with `napkin/` or `tests/` is under `napkin/engine/`. A commit is a short
SHA of this repository. The terms are those of [README.md](README.md#engine-terms) and
[the terms of the language](../language/README.md#terms).

## How to change a decision

1. Find the row of the decision on this page.
2. Change the owner, not a reader.
3. Read each reader of the row. Change a reader only where it supplies other operands, state or time.
4. Add a test that gives different answers for the old and the new rule.
5. Run the tests of the row, and the corpus families of the row.
6. When the change moves the owner, change its row on this page.

When the language leaves a result open, keep that case aside, write the question for the owner of the
project, and continue with the independent work.

The rules of the physical path:

- A held interval adds its rate times its time. A moving interval uses the method's cumulative amount
  through the accepted end.
- The engine posts a stock when a stage reads or writes it, a rate changes, a set is built again, an
  occurrence finishes, a checkpoint saves, or the run ends. A moment of one stock does work in
  proportion to the stocks that it touches.
- The engine keeps the gross amount of each leg, because the rules of frozen stocks read it.
- A post changes the books at both ends of a leg. A placement proposes posts, under the physical and
  the authored limits. The status of a stock (on a bound, on a threshold) comes from its own band.
  [methods.md](methods.md#placement-at-a-contact) tells the rules of placement and contacts.

One engine owner keeps these files together: `allocation.py`, `departure.py`,
`continuous/{bounds,fields,integrate,kernels,segment,transfers}.py`, the methods
`timeline/{way,network,component,declared,family,lines,sparse}.py`, and the timeline and run state
`timeline/{run,ways,moment,occurrences,checkpoints,saved,stocks,contacts,triggers}.py`, with the stage
targets in `timeline/plan.py`. The recorder owns the histories that a record keeps and their budget of
pieces.

## Open points

- **A cache of MovingDeclared.** MovingDeclared keys the answers of its trial states by the time and
  the clipped stock vector, and clears them when it selects a branch. A private sequence on one solver
  can reuse a trial from before its bound flags changed. Across 56 public variants, a fix that clears
  the cache at that change gave the same records. The case is for the owner of the project.
