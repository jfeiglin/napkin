# Known issues and possible future features

This page lists the known issues of the engine, the tools and the catalogue's notebooks, and the
features that could come next. Each row says what we know now. A row goes when its issue is fixed or
its feature is done: the change that does it removes the row and says so in
[CHANGELOG.md](../CHANGELOG.md).

## Known issues

| Issue | Effect | What to do now | Possible fix |
| --- | --- | --- | --- |
| **A stock that no flow moves can take a solver remainder.** In the first steps of a run, a stock whose every flow has a rate of exactly 0 can take a remainder of about 1e-27 of its unit. One model of the catalogue held 8.9e-28 h of work done before its crews started. Where the remainder enters the solver is not yet traced. | The remainder is far below the tolerance of the stock, so no check of the engine sees it. But a condition such as `x > 0` on the stock, or on a formula that reads it, reads the remainder as a value. That model's supply read "Power partly restored" for a day while no circuit was back. | In a status or an event, read the named state that the model already has, not a stock that only the solver moves. That model's share of the supply now reads 0 while the supply is off. | Keep a stock exact while every flow of it has a rate of exactly 0. This is a change of the numerical core: see [CONTRIBUTING.md](../CONTRIBUTING.md#comparisons-of-a-change-of-the-numerical-core). Then look for other conditions of the form `x > 0` on such a stock in the catalogue. |
| **A notebook waits when it runs without a browser.** Under nbclient, and so under `jupyter nbconvert --execute`, a cell that draws plotly charts into an ipywidgets `Output` widget can make the next cell wait until the timeout of the cell. | The run ends without an error, but it takes the timeout of each such cell. `fig.show()` in an `Output` widget always waits; `display(fig)` waits only for larger charts. JupyterLab is not affected. | Draw a chart with `display(fig)`, and give a short timeout, such as `--ExecutePreprocessor.timeout=60`. | Find why nbclient waits for its copy of the `Output` widget, and report it to nbclient. Or draw the charts in `go.FigureWidget`, which needs the library anywidget. |
| **The notebooks use internal names.** A notebook calls `napkin.package.combined` for a combination of options that no run declares, as `napkin run --option` does, and it uses the publisher's texts (`tools/publish/briefs.py`, `tools/publish/texts.py`). Neither is in the public API ([python-api.md](python-api.md)). | A change to these names can break a notebook, and no test finds it. | Run each notebook after a change to `napkin/package.py` or `tools/publish/`. | Make `combined` public. Add the smoke test of the notebooks (below). |
| **No test runs the notebooks.** The lint of the check reads their code, but no test runs a notebook. | A notebook can fail at a name of a model that a change removed or renamed. | Run the notebook by hand after a change to its model. | Add the smoke test of the notebooks (below). |
| **The libraries of the notebooks have no pinned versions.** jupyterlab, ipywidgets and plotly are not in `requirements.lock` or `pyproject.toml`. | A new version can change how a notebook draws its charts. Plotly 7 already differs from earlier versions in how a figure shows. | Install the versions that the notebook was tested with, if a chart does not draw. | Add an optional extra `notebook` with pinned versions, and pin them in a lock file. |
| **The analysis of the dynamics is slow on a large model.** On one run of the largest model of the catalogue (237 inputs over 25 years), `vector_field`, `equilibria` and `continue_equilibrium` together did not finish in about 3 minutes. This is one measurement, not yet profiled. | A notebook cannot offer this analysis while the reader waits. | Run the analysis by hand, apart from the notebook. | Profile `napkin.dynamics` on that model, then decide what a notebook can show. |

## Possible future features

A feature that needs more than a row has a page of its scope and its plan in the folder
`docs/scoping/`, and its row links to that page.

| Feature | What it gives | What it needs |
| --- | --- | --- |
| **Engine features for networks** ([scope and plan](scoping/networks-and-found-values.md)) | Values that the engine finds so that stated conditions hold together, with the best values by a stated goal (`find`, `make`, `goal`); lists of the things whose link names a thing; edits of the rows of a table; and models with a table in every command, in the check, in the tests and in the publisher. Any network can use them: water between utilities, medical supply, patient transfers, evacuation, electricity, fuel, markets, repair work. | A measurement of the solver paths first (S0). Then reverse lists, table edits and table models; then found values; then the reports and the run store of table runs. The owner approves the minimums of speed, a new dependency if one is necessary, and the run store of table runs. |
| **A notebook for each other package of the catalogue** (`scenarios/<package>/explore.ipynb`) | A reader changes the inputs that the story turns on and sees the outcomes. Each notebook shows what matters for its own case, as the first one does. | One notebook at a time, written for its case. For a package with many places, the notebook loads one place at a time: one place loads in about a second, all the places of the largest package in about 13 s. A run of 4 s or more needs a Run button, and a run of less than a second can follow each slider. |
| **A public API for what the notebooks use** | `combined` (a combination of options under an edit document) and `Trajectory.env_at` (the values of a run at a time) become part of the public API, so notebooks and applications use no internal names. | Entries in [python-api.md](python-api.md), and tests of the two as public functions. |
| **A smoke test of the notebooks** | A test that finds each notebook of the catalogue, checks that the committed file has no outputs, and runs it without a browser. | nbclient and ipykernel in the requirements of the tests, and a solution to the wait of the known issue above, or a short timeout. |
| **Pinned libraries for the notebooks** | The same versions of jupyterlab, ipywidgets and plotly for every reader. | An optional extra `notebook` in `pyproject.toml` and the versions in a lock file. |
| **Shared helpers for the notebooks** | One copy of the code that the notebooks repeat, such as the edit document, the text of an outcome that the model does not estimate, and the chart of each part's status. | Notebooks that repeat that code first. The helpers would go in `tools/`, read names from the model only, and name no package. |
| **Small spreads in a notebook** | The spread of the outcomes from a brief's spread (`spreads/<id>.json`), with fewer samples, while the reader waits. | The time of one run times the number of samples, shown before the start. The reader starts the spread. |
| **Charts of values that have no output** | For example a chart of the temperature that people feel at home without power. | An output with a label in the model first, so that the chart reads a value with its status and its basis. |
| **The edit document as a file** | A button that saves the edit document of the notebook's settings, for `napkin run --edits`. | A place to save it outside the checkout, so that the button does not add files to the repository. |
